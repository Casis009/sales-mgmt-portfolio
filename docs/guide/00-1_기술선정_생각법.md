# 00-1. 기술 선정: 현장에서는 이렇게 정한다

> 대상 산출물: `docs/ja/00_プロジェクト管理/01_技術選定書.md`

## 1. 일본 현장의 기술 선정 기준
개인 프로젝트는 "써 보고 싶은 기술"을 고르지만, 현장은 **"5년 동안 문제없이 유지보수할 수 있는 기술"** 을 골라요.

| 기준 | 현장에서 하는 질문 |
|---|---|
| 保守性(유지보수성) | 내가 빠져도 다른 사람이 유지보수할 수 있나? |
| サポート期間(지원 기간) | 가동 후 몇 년 동안 보안 패치가 나오나? |
| 実績(실적) | 비슷한 업무 시스템에서 써 본 사례가 많나? |
| コスト(비용) | 라이선스·운영 비용은? |
| 顧客環境(고객 환경) | 고객 PC·네트워크·보안 정책과 맞나? |

## 2. 이 프로젝트의 판단 예시
- **Spring Boot 4.2(최신)가 아니라 4.1을 고른 이유**: 4.2는 막 나와서 라이브러리(MyBatis 등) 대응이 아직 불확실해요. 현장에서는 「枯れた技術(かれたぎじゅつ, 검증이 끝난 기술)」을 선호해요.
- **JPA가 아니라 MyBatis**: 판매관리는 월 마감 집계나 장표 같은 복잡한 SQL이 많아요. SQL을 직접 쓰고 튜닝할 수 있는 쪽이 유리하고, 일본 SI 채용 공고에도 MyBatis가 자주 나와요.
- **React가 아니라 Thymeleaf**: 사용자 15명의 사내 업무 시스템에 SPA는 과해요. "필요 이상으로 복잡하게 만들지 않는다"는 판단도 설계 능력이에요.
- **SVF가 아니라 JasperReports**: SVF는 일본 장표 도구의 사실상 표준이지만 유료예요. 면접에서 「SVFも検討しましたが、コスト面でJasperReportsを採用しました」라고 말할 수 있으면 좋아요.

## 3. 「代替案(대안)」 열을 꼭 쓰는 이유
기술 선정서의 가치는 "무엇을 골랐나"보다 **"무엇과 비교해서 왜 골랐나"** 에 있어요.
고객이나 상사가 「なぜ〇〇じゃないの？」(왜 〇〇이 아니야?)라고 물었을 때 문서로 답할 수 있어야 해요.

## 4. PoC(기술 검증)를 하는 이유
문서상으로 "된다"와 실제로 "된다"는 달라요. 위험한 부분(새 버전 호환성, 일본어 PDF, ARM 서버)은 **설계를 확정하기 전에 작게 검증**해요. 나중에 안 되는 걸 알면 되돌리는 비용이 커지기 때문이에요.

## 5. 면접 한마디
> 「技術選定では、最新版よりもサポート期間と保守性を重視し、代替案との比較を技術選定書に残しました。」
> (기술 선정에서는 최신판보다 지원 기간과 유지보수성을 중시했고, 대안과의 비교를 기술 선정서에 남겼습니다.)
