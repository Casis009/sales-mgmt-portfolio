# 03-2. 처리 상세 쓰는 법

> 대상 산출물: `docs/ja/03_詳細設計/05 ~ 07`

## 1. 처리 상세서의 구성

| 절 | 내용 | 누가 쓰나 |
|---|---|---|
| クラス構成 | 어떤 클래스·메서드가 있나 | 구현자 |
| シーケンス図 | 클래스 사이의 호출 순서 | 구현자, 리뷰어 |
| 処理フロー(번호 + 에러) | 한 줄씩 무엇을 하고, 실패하면 어떤 에러인가 | 구현자, **테스터** |
| 主な SQL | 실수하기 쉬운 SQL | 구현자 |
| 同時実行時の動作 | 동시에 일어나면 어떻게 되나 | 리뷰어 |
| テスト観点 | 무엇을 확인해야 하나 | 테스터 |

**処理フロー 표가 핵심**이에요. 「No / 処理 / エラー時」 세 열로 쓰면
- 구현자는 위에서 아래로 코드를 쓰면 되고
- 테스터는 「エラー時」 열을 하나씩 테스트 케이스로 만들면 돼요.

## 2. 처리 순서에는 이유가 있다 (출하 등록의 예)

```
1. 수주 헤더 잠금        ← 가장 먼저. 이후 확인이 의미 있으려면 잠겨 있어야 함
2. version 비교          ← 싸고 빠른 체크부터
3. 상태 확인
4~7. 입력 내용 확인
8. 채번                  ← 확인이 다 끝난 뒤. 에러로 끝날 처리에 번호를 쓰지 않음
9. 재고 감산             ← 잠금이 걸리는 무거운 처리는 뒤쪽
10~13. 등록·갱신
```

원칙: **잠금 → 싼 체크 → 비싼 체크 → 갱신**. 그리고 프로젝트 전체의 잠금 순서(伝票ヘッダ → 採番 → 倉庫 → 在庫)를 지켜요.

## 3. 상태 전이는 표로 만들고 한 곳에 구현한다
발주는 상태 8개 × 조작 8개 = 64칸이에요. 이걸 각 메서드에 `if (status == …)`로 흩어 쓰면 반드시 어긋나요.

- 설계서: 표(03 문서 2장)
- 구현: `PurchaseOrderStatusPolicy` 클래스 하나
- 테스트: 64칸 전부(デシジョンテーブルテスト)

**설계서의 표 = 코드 = 테스트**가 1 : 1로 대응해요. 이게 "설계서대로 만들었다"를 증명하는 가장 쉬운 방법이에요.

## 4. 계산 로직은 DB에서 떼어 낸다
`InvoiceAmountCalculator`는 DB에 접근하지 않고 숫자만 받아 숫자를 돌려줘요. 그래서
- 테스트가 DB 없이 0.01초에 끝나고
- 경계값을 수십 개 넣어 볼 수 있어요.

소비세 계산 예(04 문서 3장)는 꼭 손으로 한 번 계산해 보세요.
- 명세별 계산: 123 + 567 + 79 = **769**
- 세율별 합계 후 계산: 691 + 79 = **770** ← 인보이스 제도상 올바른 값

"1엔 차이가 왜 생기고 어느 쪽이 맞나"를 설명할 수 있으면 일본 업무 시스템을 아는 사람으로 보여요.

## 5. 배치 설계의 핵심: 「もう一度流しても大丈夫か」
일본 현장에서 배치 리뷰 때 가장 먼저 묻는 말이 **「リランできますか？」**(다시 돌릴 수 있나요?)예요.

| 배치 | 재실행해도 되는 이유 |
|---|---|
| BAT-01 발주점 체크 | 전건 지우고 다시 만든다(洗い替え, あらいがえ) |
| BAT-02 월별 재고 | 대상 월만 지우고 다시 만든다 |
| BAT-03 청구 마감 | 미청구 출하만 대상이라, 처리된 건 자동으로 건너뛴다 |

세 가지 모두 **冪等(べきとう, 멱등)**: 몇 번 실행해도 결과가 같아요. 그래서 "어디까지 처리했나"를 기억해 뒀다 이어서 하는 복잡한 구조가 필요 없어요.

### 청크 처리 vs SQL 한 방
- BAT-01은 2,100건을 **SQL 하나(INSERT … SELECT)** 로 처리해요. 건수가 적고 판정이 SQL로 표현되니까요.
- BAT-03은 매출처 **1곳마다 커밋**해요. 한 곳이 실패해도 나머지는 살리고, 잠금 시간을 짧게 하려고요.

"Spring Batch를 쓰니까 무조건 Reader/Processor/Writer"가 아니라, **건수와 실패 시 영향으로** 방식을 골라요.

## 6. 「同時実行時の動作」 절을 쓰는 이유
평소에는 안 일어나지만 일어나면 데이터가 망가지는 경우를 미리 생각해 두는 절이에요. 표의 각 줄에 대해 "왜 괜찮은가"를 잠금이나 조건으로 설명할 수 있어야 해요.

예: 청구 마감과 출하 취소가 동시에 → 둘 다 출하 행을 `FOR UPDATE`로 잠그니까 순서대로 실행됨 → 먼저 한 쪽 결과를 보고 뒤쪽이 판단.

## 7. 単体テスト観点一覧: 설계 단계에서 테스트를 생각한다
V모델에서 상세설계의 짝이 단위 테스트예요. 설계하면서 관점을 뽑아 두면 **테스트하기 어려운 설계를 일찍 발견**해요(예: `now()` 직접 호출 → Clock 주입으로 변경).

### 관점을 뽑는 4가지 기법

| 기법 | 한 줄 설명 | 예 |
|---|---|---|
| 同値分割(どうちぶんかつ) | 같은 결과가 나오는 값들은 대표 하나만 | 발주 잔량에 넣는 상태 / 안 넣는 상태 |
| 境界値分析(きょうかいちぶんせき) | 버그는 경계에 있다. 경계의 양쪽을 본다 | 현재고 = 출하 수(가능) / 출하 수 − 1(불가) |
| デシジョンテーブル | 조건 조합을 표로 | 상태 × 조작 64칸 |
| 状態遷移テスト | 상태가 순서대로·거꾸로 바뀌는 경로 | 수주 완료 → 일부 출하 → (출하 취소) → 수주 완료 |

### 정상계만 쓰지 않기
관점 표의 「区分」 열(正常 / 異常 / 境界)을 보고 異常과 境界가 충분한지 확인해요. 정상계만 있는 테스트는 일본 현장 리뷰에서 반드시 지적받아요.

## 8. 자주 하는 실수
- 処理フロー에 "적절히 체크한다"라고 쓴다 → 무슨 체크인지, 에러 ID가 뭔지 쓴다.
- SQL을 전부 설계서에 쓴다 → 실수하기 쉬운 것(잠금, 증감 갱신, 집계)만.
- 동시 실행을 생각하지 않는다.
- 설계서를 고치지 않고 코드만 고친다 → 改訂履歴에 남긴다.
