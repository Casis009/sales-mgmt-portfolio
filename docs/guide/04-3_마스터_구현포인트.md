# 04-3. 마스터 구현 포인트(マスタ：商品・倉庫・取引先・発注点)

> 대상 코드: `master/*`(상품·창고·거래처), `common/operationlog/ChangeDetail.java`, `common/form/InputPatterns.java`
> 관련 문서: `docs/ja/02_基本設計/03_画面一覧.md`(1.3판 5.4), `03_詳細設計/07_単体テスト観点一覧.md`(1.1판 9장), `04_製造/02_コードレビュー記録票.md` 2장
> 마스터는 「단순 CRUD」로 보이지만, 업무 데이터가 모두 마스터를 참조하기 때문에 **「나중에 바뀌거나 무효가 되면 어떻게 되나」** 를 설계하는 게 핵심이에요. 면접에서 "마스터 관리에서 신경 쓴 점은?"이라고 물으면 이 문서의 3·4장을 이야기하세요.

## 1. 세 마스터의 공통 패턴

세 화면은 같은 틀로 만들었어요. 하나를 이해하면 나머지도 읽혀요.

```mermaid
flowchart LR
    L[목록<br/>MasterSearchForm] -->|검색| MP[MasterPages<br/>건수·페이징·I-010]
    F[입력 Form<br/>Bean Validation] --> V[상관 체크<br/>Validator]
    V --> S[Service<br/>@PreAuthorize·중복 E-005·낙관적 배타 E-020]
    S --> LOG[ChangeDetail<br/>바뀐 항목만 조작 로그]
```

| 규칙 | 구현 | 이유 |
|---|---|---|
| 물리 삭제하지 않고 무효화 | `enabled` 플래그 | 과거 전표가 그 마스터를 참조하고 있으니까 |
| 코드는 등록 후 변경 불가 | 갱신 SQL에 코드 컬럼 없음 + Controller가 DB 값으로 덮어씀 | 화면·CSV·사람이 코드로 기억함. 바꾸면 혼란 |
| 낙관적 배타 | `WHERE version = ?` → 0건이면 E-020 | 마스터는 「화면을 보고 있는 동안」 다른 사람이 바꿀 수 있음(共通処理設計 2.2) |
| 조작 로그는 바뀐 것만 | `ChangeDetail.change(이름, 전, 후)` | 「누가 언제 단가를 바꿨나」를 쫓을 수 있게. 변경 없는 항목은 기록하지 않음 |

## 2. 상관 체크는 어디에 두나

입력 체크에는 세 층이 있어요(共通処理設計 6장).

| 층 | 예 | 위치 |
|---|---|---|
| 단항목 | 코드 형식, 자릿수, 0~999,999,999 | Form의 `@Pattern`, `@Size`, `@Range` |
| 상관 | 「득의처면 마감일 필수」, 「표준 발주 수만 입력하면 발주점 필수」 | `PartnerFormValidator`, `ProductFormValidator` |
| 업무 | 코드 중복(E-005), 매입처가 유효한가(E-006) | Service(DB를 봐야 알 수 있는 것) |

DB에도 같은 규칙이 CHECK 제약으로 있어요(`ck_m_partner_customer_terms` 등). **화면 체크가 빠져도 DB가 마지막에 막는다** → 이중 방어예요.

### 명세 행의 함정(RV-14)
발주점은 창고마다 한 줄씩이라 `settings[0].reorderPoint` 같은 이름이 돼요. 여기에 Bean Validation을 쓰면 에러 문구가 「settings[0].reorderPointは…」처럼 나와요. 그래서 문자열로 받아 Validator에서 **「発注点（HQ 本社倉庫）は0以上999,999以下…」** 처럼 사람이 읽을 수 있는 이름으로 검사했어요. 「사용자가 보는 문구」까지 설계하는 게 일본 현장의 감각이에요.

## 3. 발주점(F-104): 「행이 없다」에도 의미가 있다

TBL-104 비고: **행이 없는 「상품 × 창고」는 발주점 체크 대상 외.** 그래서 화면 입력 → 행의 관계를 결정표로 정했어요(MS-06).

| 발주점 | 표준 발주 수 | 결과 |
|---|---|---|
| 비어 있음 | 비어 있음 | 행 없음(대상 외). 기존 행이 있으면 **삭제** |
| 입력 | 비어 있음 | 행 있음, 표준 발주 수 0 |
| 비어 있음 | 입력 | E-001(발주점 필수) |
| 입력 | 입력 | 행 있음 |

갱신은 「전부 지우고 다시 넣기」가 아니라 **행마다 추가·변경·삭제를 판정**해요. 이유는 두 가지예요.
- 지우고 다시 넣으면 `created_at`(처음 설정한 날)이 사라짐
- 조작 로그에 「HQ: 10・50→なし」처럼 무엇이 바뀌었는지 정확히 남길 수 있음

## 4. 참조처가 무효가 되면?(RV-13, MS-09)

사용자의 소속 창고가 나중에 무효가 되면, 처음 구현에서는 편집 화면의 선택지에서 그 창고가 사라졌어요. 그러면 이름만 바꿔도 「소속 창고가 무효」(E-006)로 저장이 안 돼요. 고친 규칙은 이래요.

- 선택지 = **유효한 것 + 현재 값(무효면 「（無効）」 표시)**
- 서버 체크 = **값을 바꿨을 때만** 유효성 확인

상품의 주 매입처도 같은 규칙이에요. 「새로 고르는 것」과 「원래 있던 것을 그대로 두는 것」을 구분하는 게 포인트예요.

## 5. 설계서와 다를 때: 승인된 쪽에 맞춘다

機能一覧은 F-104 이용자를 「物」, 権限マトリクス는 「物・管」으로 적고 있었어요. 구현 전에 발견했고, **나중에 승인된 権限マトリクス**에 맞춰 機能一覧을 1.3판으로 고쳤어요(개정 이력: 「権限マトリクスとの不整合を修正」). 문서끼리 어긋날 때는 마음대로 고르지 말고, 근거(어느 쪽이 승인됐나)를 대고 문서를 고치는 것까지가 일이에요.

## 6. 정직하게 남겨 둔 것
- 재고가 있거나 실사 중인 창고를 무효로 하는 것은 막지 않았어요. 재고 기능(3단계)에서 정해요(RV-17).
- 마스터 화면은 아직 브라우저로 확인하지 않았어요(RV-18).
