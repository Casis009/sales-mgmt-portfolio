## 1. 命名規約

### 1.1 設計書上の ID

| 対象 | 形式 | 例 |
|---|---|---|
| 機能 | F-NNN（百の位＝サブシステム） | F-401 |
| 画面 | SCR-NNN（百の位＝サブシステム） | SCR-402 |
| 帳票 | RPT-NN | RPT-01 |
| テーブル | TBL-NNN | TBL-301 |
| バッチ | BAT-NN | BAT-01 |
| メッセージ | 種別-NNN（I：情報、W：警告、E：エラー） | E-021 |
| 業務ルール | BR-NN | BR-03 |

### 1.2 データベース

| 対象 | 規約 | 例 |
|---|---|---|
| テーブル名 | 英小文字のスネークケース・単数形。マスタは `m_`、トランザクションは `t_` を付ける | `m_product`, `t_sales_order` |
| カラム名 | 英小文字のスネークケース。用語集の英語名を使用する | `allocated_quantity` |
| 主キー | `テーブルの主語_id`（BIGINT、自動採番） | `product_id` |
| 区分・コード | `_type`, `_status`, `_category` で終える | `movement_type` |
| 日付・日時 | 日付は `_date`、日時は `_at` で終える | `order_date`, `approved_at` |
| フラグ | 肯定形の形容詞または `is_` で始める（BOOLEAN） | `enabled`, `is_customer` |
| インデックス | `idx_テーブル名_カラム名` | `idx_t_sales_order_customer_id` |
| 外部キー制約 | `fk_子テーブル_親テーブル` | `fk_t_stock_m_product` |

### 1.3 Java

| 対象 | 規約 | 例 |
|---|---|---|
| ベースパッケージ | `jp.co.hikari.hanbai` | — |
| サブシステム | ベース直下にサブシステム識別子 | `jp.co.hikari.hanbai.sales` |
| 層 | サブシステムの下に `controller` / `form` / `service` / `mapper` / `model` | `...sales.service` |
| Controller | `画面の主語 + Controller` | `SalesOrderController` |
| Form（画面入力） | `主語 + Form` | `SalesOrderForm` |
| Service | `主語 + Service`（インターフェースは作らず、クラスのみ） | `ShipmentService` |
| Mapper | `テーブルの主語 + Mapper`（インターフェース＋同名の XML） | `SalesOrderMapper` |
| Model（テーブル対応） | テーブル名から接頭辞を除いたパスカルケース | `SalesOrder`, `SalesOrderDetail` |
| 区分値 | Enum とし、コード定義書の区分名を使用 | `SalesOrderStatus` |
| 例外 | `内容 + Exception` | `BusinessException` |
| テストクラス | `対象クラス名 + Test`（結合テストは `IT`） | `ShipmentServiceTest`, `ShipmentServiceIT` |
| テストメソッド | 日本語で「条件_期待結果」 | `現在庫数を超える出荷_エラーになる()` |

### 1.4 画面・URL

| 対象 | 規約 | 例 |
|---|---|---|
| URL | `/サブシステム/対象/操作`（英小文字・ケバブケース） | `/sales/orders/new` |
| テンプレート | `templates/サブシステム/対象-操作.html` | `sales/order-form.html` |
| 画面項目ID | Form のプロパティ名と一致させる（キャメルケース） | `deliveryDate` |

## 2. コーディング規約

1. Java の書式は Google Java Style に準拠し、Checkstyle で検査する。
2. 層の責務を守る。
   - Controller：入力の受け取り、入力チェック、Service の呼び出し、画面遷移。業務ロジックを書かない。
   - Service：業務ロジック、トランザクション境界。`@Transactional` は Service のメソッドに付ける。
   - Mapper：SQL の実行のみ。SQL は XML に記述する（アノテーションに SQL を書かない）。
3. SQL は必ずバインド変数（`#{}`）を使用する。`${}` による文字列連結は禁止する（NF-32）。
4. 金額・数量の計算に `double` / `float` を使用しない。金額は `BigDecimal`、数量は `int` とする。
5. 在庫数量の更新は、在庫管理の在庫更新サービスを通して行う。各サブシステムの Mapper から在庫テーブルを直接更新しない。
6. `null` を返すメソッドは `Optional` を返す（Mapper の単一行取得を含む）。
7. 業務エラーは `BusinessException`（メッセージID付き）を送出する。`catch` して握りつぶさない。
8. ログに個人情報・パスワードを出力しない。
9. マジックナンバー・区分値のリテラルを直接書かない（Enum・定数を使用する）。
10. コメントは「なぜそうしているか」を書く。処理内容の言い換えは書かない。公開メソッドには Javadoc を付ける。

## 3. 構成管理

### 3.1 ブランチ戦略（GitHub Flow）

| ブランチ | 用途 | ルール |
|---|---|---|
| `main` | 常にリリース可能な状態 | 直接 push 禁止。プルリクエスト経由でのみ変更する |
| `feature/機能ID-内容` | 機能の開発 | 例：`feature/F-404-shipment` |
| `fix/内容` | 不具合修正 | 例：`fix/stock-negative-check` |
| `docs/内容` | 設計書のみの変更 | 例：`docs/basic-design-screen` |

### 3.2 コミットメッセージ

```
種別: 変更内容の要約（50文字以内）

（必要に応じて）変更の理由・背景
関連: F-404, BR-15
```

種別：`feat`（機能追加）、`fix`（不具合修正）、`docs`（文書）、`test`（テスト）、`refactor`（リファクタリング）、`chore`（ビルド・設定）

### 3.3 プルリクエストとレビュー

- プルリクエストには「変更内容・関連する設計書・テスト結果」を記載する。
- CI（ビルド、静的解析、テスト）がすべて成功していることをマージの条件とする。
- 開発担当が1名のため、セルフレビューをチェックリストに沿って実施し、結果をコードレビュー記録票に残す。

### 3.4 レビューチェックリスト

| No | 観点 |
|---|---|
| 1 | 設計書（画面設計書・詳細設計書）の内容と一致しているか |
| 2 | 入力チェックがサーバー側で行われているか（画面側のチェックだけに頼っていないか） |
| 3 | 権限チェックが Controller と画面の両方にあるか |
| 4 | トランザクションの範囲は適切か。途中で失敗したときにデータが不整合にならないか |
| 5 | 在庫を更新する処理で、ロックの取得順序が守られているか |
| 6 | SQL にバインド変数を使用しているか。検索条件のカラムにインデックスがあるか |
| 7 | 操作ログが記録されるか |
| 8 | 単体テストが正常系・異常系・境界値を網羅しているか |
| 9 | 設計書と異なる実装をした場合、設計書を更新したか |

### 3.5 バージョン番号とタグ

- `v メジャー.マイナー.パッチ` とする（例：`v1.0.0`）。
- 本番リリースごとにタグを付け、リリースノート（変更内容・対象機能・DB変更の有無）を作成する。

## 4. 設計書の管理

- 設計書は Markdown で作成し、ソースコードと同じリポジトリで管理する（テスト仕様書・不具合管理表は Excel）。
- 承認済みの設計書を変更する場合は、版数を上げ、改訂履歴に記載する。
- 実装中に設計の誤りを見つけた場合は、先に設計書を修正してから実装する。
