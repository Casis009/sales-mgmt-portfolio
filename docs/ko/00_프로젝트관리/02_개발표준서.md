# 개발 표준서

> ※ 일본어 원본(정본): `docs/ja/00_プロジェクト管理/02_開発標準書.md` (1.0판, 2026/12/07)
> 설계서·소스 코드·구성 관리 규칙을 정한다. 유지보수를 넘겨받는 사람이 이 문서를 읽으면 같은 방식으로 개발을 이어갈 수 있게 하는 것이 목적이다.

## 1. 명명 규칙

### 1.1 설계서 ID

| 대상 | 형식 | 예 |
|---|---|---|
| 기능 | F-NNN(백의 자리 = 서브시스템) | F-401 |
| 화면 | SCR-NNN(백의 자리 = 서브시스템) | SCR-402 |
| 장표 | RPT-NN | RPT-01 |
| 테이블 | TBL-NNN | TBL-301 |
| 배치 | BAT-NN | BAT-01 |
| 메시지 | 종류-NNN(I: 정보, W: 경고, E: 에러) | E-021 |
| 업무 규칙 | BR-NN | BR-03 |

### 1.2 데이터베이스

| 대상 | 규칙 | 예 |
|---|---|---|
| 테이블명 | 영소문자 스네이크 케이스·단수형. 마스터는 `m_`, 트랜잭션은 `t_` | `m_product`, `t_sales_order` |
| 컬럼명 | 영소문자 스네이크 케이스. 용어집의 영어명 사용 | `allocated_quantity` |
| 기본 키 | `테이블 주어_id`(BIGINT, 자동 채번) | `product_id` |
| 구분·코드 | `_type`, `_status`, `_category`로 끝냄 | `movement_type` |
| 날짜·일시 | 날짜는 `_date`, 일시는 `_at` | `order_date`, `approved_at` |
| 플래그 | 긍정형 형용사 또는 `is_`로 시작(BOOLEAN) | `enabled`, `is_customer` |
| 인덱스 | `idx_테이블명_컬럼명` | `idx_t_sales_order_customer_id` |
| 외래 키 제약 | `fk_자식테이블_부모테이블` | `fk_t_stock_m_product` |

### 1.3 Java

| 대상 | 규칙 | 예 |
|---|---|---|
| 베이스 패키지 | `jp.co.hikari.hanbai` | — |
| 서브시스템 | 베이스 바로 아래에 서브시스템 식별자 | `jp.co.hikari.hanbai.sales` |
| 계층 | 서브시스템 아래에 `controller` / `form` / `service` / `mapper` / `model` | `...sales.service` |
| Controller | `화면 주어 + Controller` | `SalesOrderController` |
| Form(화면 입력) | `주어 + Form` | `SalesOrderForm` |
| Service | `주어 + Service`(인터페이스 없이 클래스만) | `ShipmentService` |
| Mapper | `테이블 주어 + Mapper`(인터페이스 + 같은 이름의 XML) | `SalesOrderMapper` |
| Model(테이블 대응) | 테이블명에서 접두사를 뺀 파스칼 케이스 | `SalesOrder`, `SalesOrderDetail` |
| 구분값 | Enum으로 하고 코드 정의서의 구분명 사용 | `SalesOrderStatus` |
| 예외 | `내용 + Exception` | `BusinessException` |
| 테스트 클래스 | `대상 클래스명 + Test`(통합 테스트는 `IT`) | `ShipmentServiceTest`, `ShipmentServiceIT` |
| 테스트 메서드 | 일본어로 「조건_기대 결과」 | `現在庫数を超える出荷_エラーになる()` |

### 1.4 화면·URL

## 2. 코딩 규칙
1. Java 서식은 Google Java Style을 따르고 Checkstyle로 검사한다.
2. 계층의 책임을 지킨다.
   - Controller: 입력 받기, 입력 체크, Service 호출, 화면 전이. 업무 로직을 쓰지 않는다.
   - Service: 업무 로직, 트랜잭션 경계. `@Transactional`은 Service 메서드에 붙인다.
   - Mapper: SQL 실행만. SQL은 XML에 쓴다(애너테이션에 SQL을 쓰지 않는다).
3. SQL은 반드시 바인드 변수(`#{}`)를 쓴다. `${}`로 문자열을 이어 붙이는 것은 금지(NF-32).
4. 금액·수량 계산에 `double` / `float`를 쓰지 않는다. 금액은 `BigDecimal`, 수량은 `int`.
5. 재고 수량 갱신은 재고 관리의 재고 갱신 서비스를 통해서만 한다. 각 서브시스템의 Mapper에서 재고 테이블을 직접 갱신하지 않는다.
6. `null`을 돌려줄 수 있는 메서드는 `Optional`을 돌려준다(Mapper의 단건 조회 포함).
7. 업무 에러는 `BusinessException`(메시지 ID 포함)을 던진다. `catch`해서 삼키지 않는다.
8. 로그에 개인정보·비밀번호를 출력하지 않는다.
9. 매직 넘버·구분값 리터럴을 직접 쓰지 않는다(Enum·상수 사용).
10. 주석은 「왜 그렇게 하는지」를 쓴다. 처리 내용을 되풀이해 쓰지 않는다. 공개 메서드에는 Javadoc을 붙인다.

## 3. 구성 관리

### 3.1 브랜치 전략(GitHub Flow)

| 브랜치 | 용도 | 규칙 |
|---|---|---|
| `main` | 항상 릴리스 가능한 상태 | 직접 push 금지. 풀 리퀘스트로만 변경 |
| `feature/기능ID-내용` | 기능 개발 | 예: `feature/F-404-shipment` |
| `fix/내용` | 버그 수정 | 예: `fix/stock-negative-check` |
| `docs/내용` | 설계서만 변경 | 예: `docs/basic-design-screen` |

### 3.2 커밋 메시지

```
종류: 변경 내용 요약(50자 이내)

(필요하면) 변경 이유·배경
関連: F-404, BR-15
```

종류: `feat`(기능 추가), `fix`(버그 수정), `docs`(문서), `test`(테스트), `refactor`(리팩터링), `chore`(빌드·설정)

### 3.3 풀 리퀘스트와 리뷰
- 풀 리퀘스트에는 「변경 내용·관련 설계서·테스트 결과」를 적는다.
- CI(빌드, 정적 분석, 테스트)가 모두 성공해야 머지할 수 있다.
- 개발 담당이 1명이므로 체크리스트에 따라 셀프 리뷰를 하고 결과를 코드 리뷰 기록표에 남긴다.

### 3.4 리뷰 체크리스트

| No | 관점 |
|---|---|
| 1 | 설계서(화면 설계서·상세 설계서) 내용과 일치하는가 |
| 2 | 입력 체크가 서버 쪽에서 이뤄지는가(화면 쪽 체크에만 의존하지 않는가) |
| 3 | 권한 체크가 Controller와 화면 양쪽에 있는가 |
| 4 | 트랜잭션 범위가 적절한가. 도중에 실패했을 때 데이터가 어긋나지 않는가 |
| 5 | 재고를 갱신하는 처리에서 잠금 취득 순서를 지키는가 |
| 6 | SQL에 바인드 변수를 쓰는가. 검색 조건 컬럼에 인덱스가 있는가 |
| 7 | 조작 로그가 기록되는가 |
| 8 | 단위 테스트가 정상계·이상계·경계값을 망라하는가 |
| 9 | 설계서와 다르게 구현한 경우 설계서를 갱신했는가 |

### 3.5 버전 번호와 태그
- `v 메이저.마이너.패치`(예: `v1.0.0`).
- 운영 릴리스마다 태그를 붙이고 릴리스 노트(변경 내용·대상 기능·DB 변경 유무)를 만든다.

## 4. 설계서 관리
- 설계서는 Markdown으로 만들어 소스 코드와 같은 리포지토리에서 관리한다(테스트 사양서·버그 관리표는 Excel).
- 승인된 설계서를 바꿀 때는 판수를 올리고 개정 이력에 적는다.
- 구현 중 설계 오류를 발견하면 먼저 설계서를 고친 뒤 구현한다.
