# 공통 처리 설계

> ※ 일본어 원본(정본): `docs/ja/03_詳細設計/03_共通処理設計.md` (1.0판, 2027/01/08). 시퀀스 그림은 원본 참조.

## 1. 트랜잭션

| No | 항목 | 설계 |
|---|---|---|
| 1 | 경계 | Service의 공개 메서드가 한 트랜잭션(`@Transactional`). 버튼 조작 한 번 = 한 트랜잭션 |
| 2 | 참조만 하는 처리 | `@Transactional(readOnly = true)` |
| 3 | 롤백 | 실행 시 예외(BusinessException 포함)가 던져지면 롤백. 검사 예외는 쓰지 않는다 |
| 4 | 격리 수준 | READ COMMITTED(PostgreSQL 기본값). 갱신 정합성은 격리 수준이 아니라 행 잠금으로 보장한다(2장) |
| 5 | 전파 | 기본(REQUIRED). Service에서 다른 Service를 부르면 같은 트랜잭션에 참여 |
| 6 | 예외 | 실패를 기록하는 조작 로그(로그인 실패 등)만 `REQUIRES_NEW`로 해서 업무 처리가 롤백돼도 기록을 남긴다 |
| 7 | 타임아웃 | 온라인 처리는 30초. 넘으면 롤백하고 시스템 에러(E-090) |

## 2. 배타 제어

### 2.1 기본 방침
사용자가 화면을 보고 있는 시간(수십 초~수 분)과, 등록 버튼을 누른 뒤 처리가 끝날 때까지의 시간(1초 미만)을 나눠서 생각한다.

| 대상 | 방식 | 목적 |
|---|---|---|
| 화면 표시 ~ 등록 버튼 클릭 사이 | **낙관적 배타**(version 비교) | 다른 사용자가 먼저 갱신한 내용을 모르고 덮어쓰는 것을 막는다 |
| 등록 처리 실행 중 | **비관적 배타**(행 잠금: SELECT … FOR UPDATE) | 동시에 실행된 두 처리가 같은 재고·전표를 동시에 갱신해 수량이 틀어지는 것을 막는다 |

### 2.2 마스터 갱신(낙관적 배타만)
1. 편집 화면 표시 때 `version`을 가져와 hidden 항목으로 둔다.
2. 갱신 때 `UPDATE … SET …, version = version + 1 WHERE id = ? AND version = ?` 실행.
3. 갱신 건수가 0이면 `OptimisticLockException`(E-020).

### 2.3 전표 상태를 바꾸는 처리(승인, 출하 등록, 입하 등록, 취소 등)
1. 전표 헤더를 `SELECT … FOR UPDATE`로 가져온다(같은 전표에 대한 동시 조작을 직렬화).
2. 화면에서 넘어온 `version`과 가져온 `version`을 비교. 다르면 E-020.
3. 상태가 그 조작을 할 수 있는 상태인지 확인. 아니면 E-021.
4. 명세·관련 테이블·재고 갱신.
5. 전표 헤더 갱신(`version = version + 1`).

> 1에서 행 잠금을 얻었으므로 2~5 사이에 다른 처리가 같은 전표를 갱신할 수 없다.
> 이로써 「같은 수주에 두 사람이 동시에 출하 등록해서 수주 수량을 넘겨 출하되는」 일을 막는다.

### 2.4 재고 갱신
- 재고(t_stock) 갱신은 반드시 재고 갱신 공통 부품(`StockService`, 3장)을 통해서 한다.
- `StockService`는 갱신 대상 재고 행을 `SELECT … FOR UPDATE`로 잠근 뒤 수량 확인·갱신을 한다.
- 재고는 많은 전표에서 동시에 갱신되므로 낙관적 배타(version)는 쓰지 않는다. 낙관적 배타면 같은 상품이 든 수주를 두 사람이 동시에 등록하기만 해도 한쪽이 에러가 나서 업무에 지장이 생기기 때문이다.

### 2.5 실사와의 배타(BR-05)

| 처리 | 얻는 잠금 |
|---|---|
| 입하·출하·출하 취소·재고 조정·창고 간 이동 | 대상 창고(m_warehouse 행)의 **공유 잠금**(`FOR SHARE`)을 얻은 뒤 그 창고에 진행 중인 실사가 없는지 확인 |
| 실사 시작 | 대상 창고의 **배타 잠금**(`FOR UPDATE`)을 얻은 뒤 장부 재고 수를 실사 명세에 복사 |

- 입출고끼리는 공유 잠금이라 서로 기다리지 않는다.
- 실사 시작은 실행 중인 입출고가 모두 끝날 때까지 기다린 뒤 장부 재고 수를 가져온다. 실사 시작 후에 시작된 입출고는 진행 중인 실사를 감지해 에러(E-031)가 된다.
- 수주 등록·변경·취소(할당 수만 갱신)는 실사 중에도 실행할 수 있다.

### 2.6 잠금 취득 순서(데드락 방지)
여러 행을 잠그는 처리는 반드시 아래 순서로 잠금을 얻는다.

| 순서 | 대상 | 비고 |
|---|---|---|
| 1 | 전표 헤더(수주·발주·출하·청구·실사) | 한 처리에서 잠그는 전표 헤더는 원칙적으로 하나. 출하 취소는 「수주 → 출하」 순 |
| 2 | 채번(t_numbering) | 전표 번호가 필요한 처리만. 실사 시작도 「채번 → 창고」 순 |
| 3 | 창고(실사와의 배타) | `StockService` 안에서 얻는다. 창고 간 이동은 창고 ID 오름차순 |
| 4 | 재고(t_stock) | **상품 ID·창고 ID 오름차순**으로 잠근다 |

> 예: 수주 A(상품 1·2)와 수주 B(상품 2·1)를 동시에 출하해도 둘 다 「상품 1 → 상품 2」 순으로 잠그므로 데드락이 되지 않는다.
> 만에 하나 데드락이 생기면 DB가 한쪽을 이상 종료시킨다. 이 예외는 시스템 에러(E-090)로 다루고 사용자에게 다시 조작하게 한다.

## 3. 재고 갱신 공통 부품(StockService)

### 3.1 위치
업무 규칙 BR-01~BR-05를 한 곳에서 보장한다. 재고 테이블을 갱신하는 SQL은 `StockMapper`에만 있고, `StockMapper`를 호출하는 것은 `StockService`뿐이다.

### 3.2 메서드 목록

| 메서드 | 호출처 | 현재고 수 | 할당 수 | 입출고 이력 | 실사 중 체크 | 주요 에러 |
|---|---|---|---|---|---|---|
| `allocate`(할당) | 수주 등록·변경 | — | + | — | 안 함 | — |
| `release`(할당 해제) | 수주 변경·취소·잔량 취소 | — | − | — | 안 함 | — |
| `receive`(입하) | 입하 등록 | + | — | 입하(10) | 함 | E-031 |
| `ship`(출하) | 출하 등록 | − | − | 출하(20) | 함 | E-030, E-031 |
| `cancelShipment`(출하 취소) | 출하 취소 | + | + | 출하 취소(21) | 함 | E-031 |
| `adjust`(조정) | 재고 조정 | +/− | — | 조정(30/31) | 함 | E-030, E-031 |
| `transfer`(이동) | 창고 간 이동 | 출발지 −, 도착지 + | — | 이동 출고(40)·이동 입고(41) | 함(양쪽 창고) | E-031, E-033 |
| `applyStocktaking`(실사 차이 반영) | 실사 확정 | +/− | — | 실사 차이(50/51) | 안 함(실사 확정 자신이므로) | E-030 |
| `migrate`(초기 재고) | 이관 도구 | + | — | 이관(90) | 안 함 | — |
| `findShortages`(유효 재고 부족 확인) | 수주 등록(경고 판정) | 참조만 | 참조만 | — | — | — |

인수 공통 형식: 창고 ID, 입출고일, 전표 종류·전표 번호, 명세 리스트(상품 ID, 수량), 조작자.

### 3.3 공통 처리 절차(`ship`의 예)
1. 창고의 공유 잠금을 얻는다(FOR SHARE).
2. 진행 중인 실사가 있는지 확인. 있으면 E-031.
3. 명세를 상품 ID 오름차순으로 정렬한다.
4. 명세마다: ① 재고 행이 없으면 만든다(수량 0) ② 재고 행을 잠가서 가져온다(FOR UPDATE) ③ 현재고 수 < 출하 수량이면 E-030 ④ 현재고 수·할당 수를 뺀다 ⑤ 입출고 이력 등록(증감 수, 변동 후 재고 수)

### 3.4 주요 SQL

```sql
-- 재고 행이 없으면 만든다(PostgreSQL 고유 구문)
INSERT INTO t_stock (product_id, warehouse_id, quantity, allocated_quantity,
                     created_at, created_by, updated_at, updated_by)
VALUES (#{productId}, #{warehouseId}, 0, 0, #{now}, #{userId}, #{now}, #{userId})
ON CONFLICT (product_id, warehouse_id) DO NOTHING;

-- 재고 행을 잠가서 가져온다
SELECT product_id, warehouse_id, quantity, allocated_quantity
  FROM t_stock
 WHERE product_id = #{productId} AND warehouse_id = #{warehouseId}
   FOR UPDATE;

-- 수량 갱신(증감값을 더한다. 절댓값으로 덮어쓰지 않는다)
UPDATE t_stock
   SET quantity = quantity + #{quantityDelta},
       allocated_quantity = allocated_quantity + #{allocatedDelta},
       updated_at = #{now}, updated_by = #{userId}
 WHERE product_id = #{productId} AND warehouse_id = #{warehouseId};
```

### 3.5 설계상의 주의

| No | 내용 |
|---|---|
| 1 | 수량 확인(현재고 수 ≧ 출하 수량)은 행 잠금을 얻은 **뒤에** 한다. 잠그기 전에 확인하면 확인과 갱신 사이에 다른 처리가 재고를 줄일 수 있다 |
| 2 | 갱신은 「현재 값 + 증감값」 형태로 한다. 화면에 표시하던 값을 바탕으로 덮어쓰지 않는다 |
| 3 | 할당 해제로 할당 수가 마이너스가 되는 경우(데이터 불일치)는 DB의 CHECK 제약 위반이 되어 시스템 에러로 한다. 업무 에러로 하지 않는다(프로그램 오류라 사용자가 대처할 수 없으므로) |
| 4 | `findShortages`는 잠금을 얻지 않는다. 경고 표시가 목적이고 등록을 막지 않으므로 엄밀한 일관성은 필요 없다 |
| 5 | 입출고 이력의 「변동 후 재고 수」에는 갱신 후 다시 조회한 값이 아니라, 잠가서 가져온 현재고 수 + 증감값을 넣는다(같은 트랜잭션 안에서 잠겨 있으므로 일치한다) |

## 4. 채번(NumberingService)

| 항목 | 설계 |
|---|---|
| 메서드 | `String next(SlipType 전표 종류, LocalDate 기준일)` |
| 절차 | ① 채번 테이블의 해당 행(종류·연월)이 없으면 만든다 ② 해당 행을 `FOR UPDATE`로 잠가 현재 번호를 가져온다 ③ 현재 번호 + 1로 갱신 ④ 「종류 + YYMM + 4자리 0 채움」을 돌려준다 |
| 트랜잭션 | 호출한 쪽의 트랜잭션에 참여. 업무 처리가 롤백되면 번호도 되돌아간다(결번이 생기지 않음) |
| 상한 | 9,999를 넘으면 시스템 에러 |
| 성능상 주의 | 채번 행 잠금은 트랜잭션이 끝날 때까지 유지된다. 같은 종류의 전표 등록은 직렬로 실행되지만 1건 등록이 1초 미만이라 가정 건수(성수기 80건/일)에서는 문제가 되지 않는다 |

## 5. 예외 처리

| 예외 | 의미 | 사용자 표시 | 로그 |
|---|---|---|---|
| 입력 체크 에러(BindingResult) | 단일 항목·상관 체크 위반 | 입력 화면을 다시 표시하고 항목 아래에 메시지 | 출력 안 함 |
| BusinessException | 업무 규칙 위반(재고 부족, 상태 부정 등) | 원래 화면을 다시 표시하고 메시지란에 표시 | INFO(메시지 ID만) |
| OptimisticLockException | 다른 사용자가 먼저 갱신(E-020) | 위와 같음 | INFO |
| AccessDeniedException | 권한 없음(E-012) | 에러 화면(403) | WARN(사용자·URL) |
| 그 밖의 예외 | 프로그램 오류, DB·네트워크 장애 | 에러 화면(E-090, 접수 번호) | ERROR(스택 트레이스, 접수 번호) |

- BusinessException은 Controller에서 잡는다. 입력 내용을 유지한 채 원래 화면으로 돌아가려면 그 화면의 Form과 표시용 데이터가 필요하기 때문이다.
- 접수 번호는 「일시(yyyyMMddHHmmss) + 랜덤 4자리」로 하고 에러 화면과 에러 로그 양쪽에 출력한다. 문의 때 사용자에게 접수 번호를 들으면 로그를 특정할 수 있다.
- 에러 화면에는 예외 내용·스택 트레이스·SQL을 표시하지 않는다(NF-32).

## 6. 입력 체크

| 종류 | 구현 위치 | 구현 방법 | 예 |
|---|---|---|---|
| 단일 항목 체크 | Form | Bean Validation(`@NotNull`, `@Size`, `@Min`, `@Max`, `@Pattern`). 메시지는 E-001~E-004에 대응 | 수량은 1 이상 999,999 이하 |
| 상관 체크 | Form에 대응하는 Validator 클래스 | Spring의 `Validator`를 구현해 Controller에서 실행 | 명세 1행 이상, 같은 상품 중복 없음 |
| 마스터 존재 체크 | Service | 대상 마스터를 가져와 존재·유효 확인 | 유효한 매출처일 것(E-006) |
| 업무 체크 | Service | 트랜잭션 안에서 잠금을 얻은 뒤의 데이터로 확인 | 현재고 수, 상태, 잔량 |

- 화면 쪽(JavaScript) 체크는 입력 편의를 위한 보조다. 서버 쪽 체크를 생략하지 않는다.
- 명세 행은 상품 코드가 빈 행을 뺀 뒤 체크한다.
- 문자열 항목은 앞뒤 공백을 뺀 뒤 체크한다(공백만 입력한 것은 미입력으로 본다).

## 7. 조작 로그

| 대상 | 방법 |
|---|---|
| 업무 조작(등록·갱신·취소·승인·확정·출력) | Service 메서드에 `@OperationLogged`를 붙인다. `OperationLogAspect`가 메서드 정상 종료 후 같은 트랜잭션에서 조작 로그 등록 |
| 로그인·로그아웃 | Spring Security 인증 이벤트를 `AuthenticationEventListener`로 받아 조작 로그 등록 |
| 배치 | 잡 시작·종료 때 리스너로 등록 |

- 메서드 반환값(전표 번호·코드)을 「대상 키」로 기록한다.
- 「조작 내용」에는 주요 항목(수량·금액·상태의 변경 전후)을 기록한다. 비밀번호는 기록하지 않는다.
- 업무 처리가 롤백되면 조작 로그도 등록되지 않는다(같은 트랜잭션이므로). 실패한 조작은 애플리케이션 로그로 확인한다.
- 조회(목록 검색·상세 표시)는 기록하지 않는다. 건수가 너무 많아져 필요한 로그를 찾기 어려워지기 때문이다. 장표·CSV 출력은 데이터 반출에 해당하므로 기록한다.

## 8. 로그 출력

| 로그 | 출력처 | 내용 | 레벨 | 보유 |
|---|---|---|---|---|
| 애플리케이션 로그 | `logs/application.log` | 처리 시작·종료, 업무 에러, 배치 처리 건수 | INFO 이상 | 90일(일별 로테이션) |
| 에러 로그 | `logs/error.log` | 시스템 에러의 스택 트레이스, 접수 번호 | ERROR | 90일 |
| 접근 로그 | Nginx | 요청 일시, URL, 상태, 응답 시간 | — | 90일 |
| 조작 로그 | DB(t_operation_log) | 7장 | — | 5년 |

- 형식: `일시 레벨 [요청 ID] [로그인 ID] 클래스명 - 메시지`. 요청 ID·로그인 ID는 MDC에 설정.
- 운영 환경에서는 SQL을 로그에 출력하지 않는다(개발 환경만 DEBUG로 출력).
- 개인정보·비밀번호·세션 ID를 출력하지 않는다.

## 9. PostgreSQL 고유 구문 사용처
향후 DBMS 이전 때 고쳐야 할 곳을 아래로 한정한다.

| No | 구문 | 사용처 | 용도 |
|---|---|---|---|
| 1 | `INSERT … ON CONFLICT DO NOTHING` | StockMapper, NumberingMapper | 행이 없으면 만든다 |
| 2 | `FOR SHARE` | WarehouseMapper | 실사와의 배타 |
| 3 | `LIMIT … OFFSET …` | 각 목록 검색 | 페이징 |
| 4 | 부분 인덱스(`CREATE INDEX … WHERE …`) | DDL(실사, 출하) | 조건부 일의 제약·검색 고속화 |
| 5 | `GENERATED ALWAYS AS IDENTITY` | DDL | 기본 키 자동 채번(SQL 표준이지만 DBMS마다 차이 있음) |

## 10. 그 밖의 공통 처리

| 항목 | 설계 |
|---|---|
| 이중 전송 방지 | ① 등록 후 리다이렉트(PRG 패턴) ② 버튼 클릭 후 비활성화 ③ 입력 화면 표시 때 토큰을 발급해 세션에 두고 등록 때 대조·파기. 불일치면 처리하지 않고 목록 화면으로 이동 |
| 페이징 | 검색 조건 Form에 `page`(1부터). 건수 조회 SQL과 목록 조회 SQL(`LIMIT 50 OFFSET (page−1)×50`) 실행. 건수가 5,000건을 넘으면 W-002 표시 |
| 현재 일시 | `Clock`을 DI해 `LocalDate.now(clock)` / `LocalDateTime.now(clock)`로 얻는다. 시간대는 Asia/Tokyo. DB의 `now()`는 쓰지 않는다(테스트에서 고정할 수 없으므로) |
| 소비세 계산 | `TaxCalculator.calculate(대상액, 세 구분, 기준일)`: 소비세율 마스터에서 기준일 시점 세율을 가져와 `대상액 × 세율`을 `RoundingMode.DOWN`으로 정수화. `BigDecimal`로 계산 |
| 마감일·지급 기한 계산 | `ClosingDateCalculator`: 마감일 구분 99는 그 달 말일, 1~28은 그 날. 지급 기한은 마감일이 속한 달에 지급 월 구분을 더하고 지급일(99는 말일)을 적용 |
| 장표 출력 | `ReportService.exportPdf(장표 ID, 파라미터, 명세)`: 컴파일된 장표 정의를 캐시하고 PDF를 바이트 배열로 돌려준다. Controller는 `Content-Type: application/pdf`로 응답 |
