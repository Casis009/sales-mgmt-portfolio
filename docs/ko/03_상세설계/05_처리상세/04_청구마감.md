# 처리 상세: 청구 마감·마감 취소·청구서 출력

> ※ 일본어 원본(정본): `docs/ja/03_詳細設計/05_処理詳細/04_請求締め.md` (1.0판, 2027/01/14). 시퀀스도·SQL은 원본 참조.
> 대응 기본설계: 화면 설계서 SCR-501, 장표 설계서 RPT-01, 배치 목록 BAT-03, BR-31~36

## 1. 클래스 구성

| InvoiceClosingService | `findTargetCustomerIds(마감일, 마감일 구분, 매출처 ID)` | 대상 매출처 ID 조회(배치 입력) |
| InvoiceClosingService | `closeCustomer(매출처 ID, 마감일, 실행자)` | **매출처 1곳분의 청구 생성(한 트랜잭션)** |

| ClosingDateCalculator | `closingDate(대상 연월, 마감일 구분)` / `paymentDueDate(마감일, 지급 월 구분, 지급일)` | 날짜 계산 |

## 2. 매출처 1곳분의 청구 생성(InvoiceClosingService.closeCustomer)

| No | 처리 | 비고 |
|---|---|---|
| 1 | 매출처 마스터 조회(마감일 구분, 지급 조건) | — |
| 2 | 대상 출하를 `FOR UPDATE`로 가져온다. 조건: 매출처 ID 일치, 상태 = 출하 완료(10), 청구 ID IS NULL, 출하일 ≦ 마감일. 출하일·출하 번호 오름차순 | 0건이면 아무것도 하지 않고 종료(다른 실행에서 이미 처리된 경우 등) |
| 3 | 대상 출하의 출하 명세 조회(품명·단위는 상품 마스터에서) | — |
| 4 | `InvoiceAmountCalculator.calculate`로 금액 계산(3장) | — |
| 5 | 대상 기간을 구한다. 시작일: 그 매출처의 취소가 아닌 청구 중 가장 최근 마감일의 다음 날(청구가 없으면 대상 출하 중 가장 오래된 출하일). 종료일: 마감일 | 시작일보다 앞선 출하일의 출하가 들어갈 수 있다(나중에 등록된 과거 날짜 출하) |
| 6 | 지급 기한 계산(`ClosingDateCalculator.paymentDueDate`) | — |
| 7 | 청구 번호 채번(IV, 마감일의 연월) | — |
| 8 | 청구 등록(상태: 확정, 발행 횟수: 0) | — |
| 9 | 청구 명세 등록(출하 명세 1행당 1행. 품명·단위·단가·금액·세 구분 복사) | — |
| 10 | 대상 출하의 청구 ID 갱신(2번에서 가져온 출하 ID 지정) | 갱신 건수가 2번 건수와 다르면 시스템 에러 |

## 3. 청구 금액 계산(InvoiceAmountCalculator)

| No | 처리 |
|---|---|
| 1 | 출하 명세 금액을 세 구분별로 합계(10% 대상액, 8% 대상액) |
| 2 | 세 구분별로 마감일 시점 세율을 소비세율 마스터에서 가져온다 |
| 3 | 소비세액 = 대상액 × 세율. 1엔 미만 버림(`RoundingMode.DOWN`) |
| 4 | 청구 금액 = 10% 대상액 + 10% 소비세액 + 8% 대상액 + 8% 소비세액 |

### 계산 예

| 명세 | 금액(세전) | 세 구분 |
|---|---|---|
| A | 1,234 | 표준(10%) |
| B | 5,678 | 표준(10%) |
| C | 999 | 경감(8%) |

- 10% 대상액 = 6,912, 소비세액 = 691.2 → **691**
- 8% 대상액 = 999, 소비세액 = 79.92 → **79**
- 청구 금액 = 6,912 + 691 + 999 + 79 = **8,681**

> 명세별로 소비세를 계산해 합치면 A: 123, B: 567, C: 79로 합계 769가 되어 위의 770(691 + 79)과 맞지 않는다.
> 인보이스 제도에서는 「청구서 1장당 세율별 1회」 끝수 처리로 정해져 있으므로 반드시 합계한 뒤 계산한다(BR-34).

- 계산은 모두 `BigDecimal`로 한다. `double`은 쓰지 않는다.
- 이 클래스는 DB에 접근하지 않는다(세율은 인수로 받는다). 단위 테스트에서 많은 조합을 빠르게 검증하기 위해서다.

## 4. 날짜 계산(ClosingDateCalculator)

| 입력 | 결과 |
|---|---|
| 대상 연월 2027/04, 마감일 구분 99(말일) | 마감일 2027/04/30 |
| 대상 연월 2027/02, 마감일 구분 99 | 마감일 2027/02/28 |
| 대상 연월 2028/02, 마감일 구분 99 | 마감일 2028/02/29(윤년) |
| 대상 연월 2027/04, 마감일 구분 20 | 마감일 2027/04/20 |
| 마감일 2027/01/31, 지급 월 구분 1(다음 달), 지급일 99 | 지급 기한 2027/02/28 |
| 마감일 2027/04/20, 지급 월 구분 1, 지급일 20 | 지급 기한 2027/05/20 |
| 마감일 2027/12/31, 지급 월 구분 2(다다음 달), 지급일 10 | 지급 기한 2028/02/10 |

지급 기한이 토·일·공휴일이어도 조정하지 않는다(현행 청구서와 같은 취급).

## 5. 마감 취소(InvoiceService.cancel)
권한: `hasRole('ACCOUNTING')`, 조작 로그: CANCEL / SCR-503 / t_invoice

| No | 처리 | 에러 시 |
|---|---|---|
| 1 | 청구를 `FOR UPDATE`로 가져와 version 비교 | E-020 |
| 2 | 상태가 「確定(10)」인지 확인(BR-36) | 발행 완료: E-051, 취소: E-021 |
| 3 | 이 청구에 연결된 출하의 청구 ID를 NULL로 되돌린다 | — |
| 4 | 청구 상태를 「取消(90)」로 갱신. version + 1 | — |

- 청구 명세는 지우지 않는다(취소한 청구 내용을 확인할 수 있게).
- 취소 후 다시 청구 마감을 실행하면 새 청구 번호로 청구가 만들어진다.

## 6. 청구서 PDF 출력(InvoiceService.exportPdf)
권한: `hasRole('ACCOUNTING')`, 조작 로그: EXPORT / SCR-503 / t_invoice

| No | 처리 | 에러 시 |
|---|---|---|
| 1 | 청구를 `FOR UPDATE`로 가져온다 | — |
| 2 | 상태가 「확정」 또는 「발행 완료」인지 확인 | E-021 |
| 3 | 발행 횟수를 1 더한다. 첫 회(0 → 1)면 상태를 「발행 완료」, 발행 일시를 현재 일시로 갱신 | — |
| 4 | 청구 명세·매출처·자사 정보 조회 | — |
| 5 | `ReportService.exportPdf("RPT-01", …)`로 PDF 생성. 발행 횟수가 2 이상이면 「再発行」 표시 | — |

- 금액은 청구 테이블 값을 그대로 인쇄한다(다시 계산하지 않음).
- PDF 생성에 실패하면 트랜잭션이 롤백되어 발행 횟수가 더해지지 않는다.

## 7. 동시 실행 시 동작

| 경우 | 동작 |
|---|---|
| 청구 마감 실행 중에 같은 매출처의 출하가 등록됨 | 커밋 전 출하는 2번에서 잡히지 않아 이번 청구에 들어가지 않는다. 다음 청구 마감 대상이 된다 |
| 청구 마감과 출하 취소가 동시에 실행됨 | 출하 행 잠금으로 직렬화. 청구 마감이 먼저: 출하 취소는 E-045. 출하 취소가 먼저: 그 출하는 청구 마감 대상에서 빠진다 |
| 두 사람이 동시에 청구 마감 실행 | 잡 이중 기동 체크로 뒤쪽은 E-052. 만에 하나 동시에 실행돼도 출하 행 잠금과 「청구 ID IS NULL」 조건 때문에 같은 출하가 두 청구에 들어가지 않는다 |
| 청구 마감 도중 이상 종료 | 처리된 매출처의 청구는 확정돼 있다. 다시 실행하면 처리되지 않은 매출처만 청구가 만들어진다 |

## 8. 단위 테스트에서 확인할 주요 관점
- 3장 계산 예와 「07 단위 테스트 관점 목록」의 소비세 계산 관점
- 4장 날짜 계산 전 패턴
- 마감일 뒤의 출하, 취소된 출하, 청구된 출하가 대상이 되지 않을 것
- 마감 취소 후 다시 마감하면 같은 출하가 새 청구에 들어갈 것
- 발행된 청구는 취소할 수 없을 것. 두 번째 출력에서 발행 횟수가 2가 되고 발행 일시는 바뀌지 않을 것
