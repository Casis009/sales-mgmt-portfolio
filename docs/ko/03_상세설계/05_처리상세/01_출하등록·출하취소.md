# 처리 상세: 출하 등록·출하 취소

> ※ 일본어 원본(정본): `docs/ja/03_詳細設計/05_処理詳細/01_出荷登録・出荷取消.md` (1.0판, 2027/01/12). 클래스도·시퀀스도는 원본 참조.
> 대응 기본설계: 화면 설계서 SCR-405, 화면 목록 SCR-403, BR-03, 04, 05, 14, 15, 17

## 1. 클래스 구성

| 클래스 | 메서드 | 개요 |
|---|---|---|
| ShipmentController | `GET /sales/orders/{id}/shipments/new` | `prepare` 결과를 Form에 넣어 SCR-405 표시 |
| ShipmentController | `POST /sales/orders/{id}/shipments` | 입력 체크 → `register` → SCR-403으로 리다이렉트. BusinessException이면 SCR-405 다시 표시 |
| ShipmentController | `POST /sales/shipments/{id}/cancel` | `cancel` → SCR-403으로 리다이렉트 |
| ShipmentForm | — | 수주 ID, 수주 version, 출하일, 비고, 명세(수주 행 번호, 이번 출하 수) |
| ShipmentService | `register(command, user)` | 2장. 출하 번호를 돌려준다 |
| ShipmentService | `cancel(출하 ID, version, user)` | 4장 |
| 의존 | SalesOrderMapper, ShipmentMapper, NumberingService, StockService | |

## 2. 출하 등록(ShipmentService.register)
권한: `@PreAuthorize("hasRole('WAREHOUSE')")`, 조작 로그: CREATE / SCR-405 / t_shipment

| No | 처리 | 에러 시 |
|---|---|---|
| 1 | 수주 헤더를 `FOR UPDATE`로 가져온다 | 없음: 시스템 에러 |
| 2 | 화면에서 받은 version과 비교 | 불일치: E-020 |
| 3 | 상태가 「受注済(10)」 또는 「一部出荷(20)」인지 확인 | E-021 |
| 4 | 출하일이 수주일 이후이고 당일 이전인지 확인 | E-007 |
| 5 | 수주 명세를 가져와 입력된 명세(수주 행 번호·이번 출하 수)와 맞춰 본다. 이번 출하 수가 0인 행은 제외 | 수주 명세에 없는 행 번호: 시스템 에러 |
| 6 | 출하할 명세가 1행 이상인지 확인 | E-044 |
| 7 | 명세마다 「이번 출하 수 ≦ 수주 수량 − 출하 완료 수량」 확인 | E-043 |
| 8 | 출하 번호 채번(SH, 출하일의 연월) | — |
| 9 | `StockService.ship` 호출(창고 = 수주의 출하 창고) | E-031, E-030 |
| 10 | 출하 등록(상태: 출하 완료, 청구 ID: NULL, 매출처 ID·창고 ID는 수주에서 복사) | — |
| 11 | 출하 명세 등록(단가·세 구분은 수주 명세에서 복사, 금액 = 이번 출하 수 × 단가) | — |
| 12 | 수주 명세의 출하 완료 수량에 이번 출하 수를 더한다 | — |
| 13 | 수주 헤더 갱신. 전 명세가 「출하 완료 수량 = 수주 수량」이면 「出荷完了(30)」, 아니면 「一部出荷(20)」. version + 1 | — |
| 14 | 출하 번호를 돌려준다 | — |

주요 SQL(수주 헤더 잠금, 출하 완료 수량 가산, 수주 헤더 갱신)은 원본 2.3 참조. 출하 완료 수량은 `shipped_quantity = shipped_quantity + #{quantity}`처럼 증감값으로 갱신한다.

## 3. 동시 실행 시 동작

| 경우 | 동작 |
|---|---|
| 같은 수주에 두 사람이 동시에 출하 등록 | 나중에 온 처리는 1번 잠금에서 기다리다가 앞 처리의 커밋 후 version 불일치(E-020)가 된다. 수주 수량을 넘는 출하는 생기지 않는다 |
| 다른 수주지만 같은 상품을 동시에 출하 | 재고 행 잠금으로 직렬 실행. 뒤 처리는 앞 처리로 줄어든 뒤의 현재고 수로 부족을 판정(E-030) |
| 출하 등록 중에 실사가 시작됨 | 실사 시작은 창고 배타 잠금으로 출하 커밋을 기다린다. 출하는 실사 시작 전 재고로 반영된다 |
| 출하 등록 중에 청구 마감이 실행됨 | 커밋 전 출하는 청구 마감에서 보이지 않는다. 커밋 후 다음 청구 마감 대상이 된다 |

## 4. 출하 취소(ShipmentService.cancel)
권한: `hasRole('WAREHOUSE')`, 조작 로그: CANCEL / SCR-403 / t_shipment

| No | 처리 | 에러 시 |
|---|---|---|
| 1 | 출하에서 수주 ID를 얻어 수주 헤더를 `FOR UPDATE`로 가져온다(잠금 순서: 수주 → 출하) | — |
| 2 | 출하를 `FOR UPDATE`로 가져와 화면의 version과 비교 | E-020 |
| 3 | 출하 상태가 「出荷済(10)」인지 확인 | E-021 |
| 4 | 출하의 청구 ID가 NULL인지 확인 | E-045(청구 번호 표시) |
| 5 | 수주의 잔량 취소 플래그가 false인지 확인 | E-046 |
| 6 | `StockService.cancelShipment` 호출(현재고 수·할당 수 가산, 입출고 이력: 출하 취소. 전표 번호는 원래 출하 번호) | E-031 |
| 7 | 수주 명세의 출하 완료 수량에서 출하 명세 수량을 뺀다 | — |
| 8 | 수주 헤더 상태 재계산(전 명세의 출하 완료 수량이 0: 「受注済」, 아니면 「一部出荷」). version + 1 | — |
| 9 | 출하 상태를 「取消(90)」로 갱신. version + 1 | — |

> 청구 마감 배치는 대상 출하를 `FOR UPDATE`로 잠가서 청구 ID를 설정한다. 출하 취소의 2번 잠금과 겹치므로 「취소와 동시에 청구되는」 일은 없다.

## 5. 단위 테스트에서 확인할 주요 관점
- 전량 출하면 「出荷完了」, 일부 출하면 「一部出荷」가 될 것
- 이번 출하 수가 잔량과 같음(경계값: 가능), 잔량 + 1(불가)
- version 불일치, 상태 부정(취소됨, 출하 완료)에서 에러가 될 것
- 출하 취소 후 수주 명세·상태·재고·할당이 출하 전 값으로 돌아올 것
