# 소프트웨어 구성

> ※ 일본어 원본(정본): `docs/ja/03_詳細設計/02_ソフトウェア構成.md` (1.1판, 2027/01/25: 제조(공통) 결과 반영. common에 controller·form·menu 추가, 인증용 SQL을 LoginUserMapper로 분리, master에 dto 추가, Bean Validation 메시지를 messages.properties로 통합, 공통 부품·설계 방침 No.8 추가). 그림은 원본 참조.

## 1. 전체 구성
Spring Boot 애플리케이션 하나(jar 하나)로 구성한다. 화면·업무 처리·장표·배치를 같은 애플리케이션에 넣는다.

브라우저 →(HTTPS)→ Nginx → Spring Security(인증·인가·CSRF) → Controller → Service → Mapper(MyBatis) → PostgreSQL. 스케줄러 → 배치(Spring Batch) → Service. Service → 장표 출력(JasperReports). 조작 로그(AOP)가 Service에 걸린다.

## 2. 계층의 책임

| 계층 | 책임 | 하면 안 되는 것 |
|---|---|---|
| Controller | 요청 받기, Form 변환, 단일 항목·상관 체크 실행, Service 호출, 화면(템플릿) 선택, 메시지 설정 | 업무 로직, Mapper 직접 호출, 트랜잭션 제어 |
| Form | 화면 입력값 보관. Bean Validation 애너테이션으로 단일 항목 체크 정의 | DB 접근, Model(테이블 대응 클래스)과 겸용 |
| Service | 업무 로직, 업무 체크, 트랜잭션 경계, 다른 Service 호출 | HTTP에 의존하는 처리(세션·요청 참조). 로그인 사용자는 인수로 받는다 |
| Mapper | SQL 실행. Mapper 하나가 주 테이블 하나(와 그 명세)를 담당 | 업무상 판단(if 분기 등). 동적 SQL은 검색 조건 조립에만 |
| Model | 테이블 한 행에 대응하는 데이터 보관 | 화면 표시용 편집 |
| Dto | 여러 테이블을 조인한 검색 결과, Service 간 전달 데이터(record로 정의) | — |

### 호출 규칙
- Controller → Service → 같은 서브시스템의 Mapper / 의존 대상 서브시스템의 Service
- **금지:** Controller → Mapper, Service → 다른 서브시스템의 Mapper
- 다른 서브시스템의 테이블을 갱신할 때는 반드시 그 서브시스템의 Service를 호출한다(예: 출하 등록은 재고를 직접 갱신하지 않고 `StockService` 호출).
- 다른 서브시스템의 마스터를 **참조**만 할 때도 그 서브시스템의 Service(또는 참조 전용 Query Service)를 거친다.
- 서브시스템 간 의존 방향은 「기능 구성도」 2장을 따른다(순환 의존 금지).

## 3. 패키지 구성

```
jp.co.hikari.hanbai
├── HanbaiApplication.java
├── common                          공통
│   ├── controller / form           공통 화면(SCR-001 로그인, SCR-002 메뉴, SCR-003 비밀번호 변경, SCR-013 조작 로그 조회)
│   ├── menu                        메뉴·대시보드 표시 내용(MenuService, DashboardService)
│   ├── config                      설정(Security, MyBatis, Batch, Web, Clock)
│   ├── security                    인증·인가(LoginUser, LoginUserDetailsService, 인증 이벤트 리스너, LoginUserMapper, 비밀번호 변경)
│   ├── exception                   예외(BusinessException, OptimisticLockException, GlobalExceptionHandler)
│   ├── operationlog                조작 로그(@OperationLogged, OperationLogAspect, OperationLogService, Mapper)
│   ├── numbering                   채번(NumberingService, NumberingMapper)
│   ├── message                     메시지 ID 상수, 메시지 조회
│   ├── code                        구분값 Enum(SlipType, TaxCategory 등), MyBatis TypeHandler
│   ├── web                         화면 공통(페이징, 이중 전송 방지, 공통 ModelAttribute)
│   ├── report                      장표 출력 공통 부품(ReportService)
│   └── util                        날짜 계산(마감일·지급 기한), 소비세 계산
├── master                          마스터 관리(controller / form / service / mapper / model / dto)
├── stock                           재고 관리(+ dto, batch: BAT-02 월별 재고 집계)
├── purchase                        구매 관리(+ dto, batch: BAT-01 발주점 체크)
├── sales                           판매 관리(+ dto)
└── billing                         청구 관리(+ dto, batch: BAT-03 청구 마감)
```

리소스(`src/main/resources`): `application.yml`(+ 환경별 `-dev` / `-stg` / `-prd`), `messages.properties`(Bean Validation 메시지도 에러 코드를 키로 같은 파일에 정의), `db/migration`(Flyway DDL·초기 데이터), `mapper/{서브시스템}/*.xml`, `templates/{서브시스템}/*.html`, `templates/fragments`(공통 레이아웃), `static/css`·`static/js`, `reports/*.jrxml`(RPT-01, RPT-02), `fonts`(IPAex 고딕)

## 5. 설계 방침

| No | 방침 | 이유 |
|---|---|---|
| 1 | Service는 인터페이스 없이 클래스만 만든다 | 구현이 하나뿐인 인터페이스는 유지보수 부담만 늘린다. 테스트에서는 Mockito로 클래스를 목으로 만들 수 있다 |
| 2 | Form과 Model을 나눈다 | 화면 항목과 테이블 컬럼은 일치하지 않는다(표시 전용 항목, 명세 배열 등). 겸용하면 화면에서 의도하지 않은 컬럼이 갱신될 위험이 있다 |
| 3 | 현재 일시는 `Clock`을 DI해서 얻는다(`LocalDate.now(clock)`) | 마감일·월 바뀜 등 날짜에 의존하는 처리를 테스트에서 날짜를 고정해 검증하기 위해 |
| 4 | 구분값은 Enum으로 하고 MyBatis TypeHandler로 DB 값과 상호 변환한다 | SQL에도 Java에도 구분값 리터럴을 쓰지 않기 위해 |
| 5 | 검색 결과는 Model이 아니라 Dto(record)로 받는다 | 목록 화면은 여러 테이블의 조인 결과라 테이블 한 행에 대응하지 않으므로 |
| 6 | 배치의 업무 로직도 Service에 두고, 배치 클래스는 기동·진행 관리만 한다 | 화면과 배치가 같은 로직을 공유하고 단위 테스트를 Service에 모으기 위해 |
| 7 | PostgreSQL 고유 구문은 사용처를 한정해 목록화한다(공통 처리 설계 9장) | 향후 DBMS 이전 시 영향 범위를 분명히 하기 위해 |
| 8 | 트랜잭션 AOP를 바깥, 조작 로그 AOP(`@OperationLogged`)를 안쪽으로 두고 순서를 명시한다. 조작 로그 등록은 `Propagation.MANDATORY` | 기본값에서는 둘 다 최저 우선이라 순서가 보장되지 않고, 조작 로그가 업무와 다른 트랜잭션으로 등록될(업무가 롤백돼도 로그만 남을) 수 있기 때문. MANDATORY로 순서 오류를 예외로 검출 |
