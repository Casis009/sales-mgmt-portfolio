# 배치 상세 설계

> ※ 일본어 원본(정본): `docs/ja/03_詳細設計/06_バッチ詳細設計.md` (1.1판, 2027/01/18. 1.0판 2027/01/14). 구성도·시퀀스도·SQL은 원본 참조.
> 1.1판 변경: 기술 검증 P-05 결과로 공통 부품 클래스명과 Spring Batch 6 구현 방법 확정(1.1), 청구 마감 Reader를 @StepScope로(4.1), 기동 시 복구 처리 클래스명 기재(5장).
> Spring Batch는 6.0 계열(Spring Boot 4.1.3 관리 6.0.6)을 쓴다. 잡 기동에는 JobLauncher가 아니라 JobOperator를 쓴다(기술 검증 결과 보고서 6장 No.3).

## 1. 공통 구성

| 항목 | 설계 |
|---|---|
| 잡 정의 | 각 서브시스템의 `batch` 패키지에 잡별 설정 클래스를 둔다 |
| 업무 로직 위치 | Service에 둔다. 잡·스텝 클래스는 Service 호출과 건수 기록만 한다 |
| 기동 시 자동 실행 | 끈다(애플리케이션 기동 때 잡이 실행되지 않게) |
| 스케줄 | `BatchScheduler`에 `@Scheduled(cron = …, zone = "Asia/Tokyo")`로 정의. cron 식은 설정 파일에서 바꿀 수 있게 |
| 잡 파라미터 | 업무 파라미터에 더해 실행마다 다른 값(기동 일시)을 붙인다. 같은 업무 파라미터로 몇 번이든 실행할 수 있게 하기 위해서다 |
| 실행 이력 | Spring Batch 실행 관리 테이블(`BATCH_*`)에 기록 |
| 공통 리스너(JobLogListener) | 잡 시작·종료 때 애플리케이션 로그와 조작 로그(BATCH) 출력. 이상 종료 때는 ERROR 로그 출력(모니터링이 감지) |
| 실행 사용자 | 스케줄 기동 배치는 등록자·갱신자를 0(시스템)으로 |

기동 경로: `BatchScheduler`(@Scheduled) 또는 `InvoiceClosingController`(화면) → `JobLaunchService`(잡 기동 부품) → 각 잡 → Service

### 1.1 공통 부품(기술 검증 P-05에서 확정)

| 클래스(패키지) | 역할 |
|---|---|
| `BatchConfig`(common.config) | `@BatchTaskExecutor`를 붙인 ThreadPoolTaskExecutor(스레드 수 `hanbai.batch.pool-size`, 기본 3) 정의. Spring Boot가 자동 구성하는 JobOperator가 이 스레드에서 잡을 실행하므로 기동이 비동기가 된다 |
| `JobLaunchService`(common.batch) | 잡 기동 부품. `launch(Job, 업무 파라미터)`: 같은 잡이 실행 중이면 E-052 BusinessException, 아니면 `launchedAt`을 붙여 JobOperator로 기동하고 실행 ID 반환. 이중 기동 확인과 기동은 synchronized로 직렬화(앱은 1대 구성). `findProgress(잡 이름, 실행 ID)`: 상태(RUNNING/COMPLETED/FAILED)와 모든 스텝의 읽기·쓰기 건수 반환. 실행 ID가 없거나 다른 잡이면 빈 값(화면은 404) |
| `JobProgress`(common.batch) | 실행 상황(record). 4.2의 응답 내용 |
| `JobLogListener`(common.batch) | 공통 리스너. 조작 로그(BATCH) 기록은 조작 로그 부품을 만드는 구현 2단계에서 추가 |
| `StaleJobExecutionRecoverer`(common.batch) | 기동 시 복구 처리(5장). ApplicationRunner로서 실행 중인 채 남은 잡 실행을 JobOperator#recover로 이상 종료로 갱신 |
| `ReorderPointCheckJobConfig`(purchase.batch), `MonthlyStockSummaryJobConfig`(stock.batch), `InvoiceClosingJobConfig`(billing.batch) | 잡별 설정 클래스(구현 6단계에서 작성) |
| `BatchScheduler`(common.batch) | 스케줄 기동(구현 6단계에서 작성) |

## 2. BAT-01 발주점 체크(reorderPointCheckJob)

| 항목 | 내용 |
|---|---|
| 기동 | 매일 22:00(cron: `0 0 22 * * *`) |
| 파라미터 | `alertDate`(실행일), `launchedAt` |
| 구성 | 1스텝(태스크릿). `ReorderAlertService.rebuild(alertDate)` 호출 |
| 트랜잭션 | 전체가 한 트랜잭션(삭제와 등록을 함께 확정) |

처리(ReorderAlertService.rebuild): ① `DELETE FROM t_reorder_alert` ② INSERT … SELECT로 추출 결과 등록(상품 창고 설정 × 유효한 상품·창고, 재고와 발주 잔량(상태 20·30·40)을 LEFT JOIN, 조건: 발주점 > 0이고 유효 재고 수 + 발주 잔량 ≦ 발주점) ③ 등록 건수 반환

| No | 판단 | 이유 |
|---|---|---|
| 1 | 1건씩 읽어 판정하는 방식(청크 처리)이 아니라 SQL 하나로 추출·등록 | 대상이 최대 2,100건이라 집합 연산으로 몇 초 안에 끝난다. 1건씩 처리하는 방식은 건수가 적은 이 처리에서는 복잡해지기만 한다 |
| 2 | 전체 교체(전건 삭제 → 등록) | 몇 번 실행해도 결과가 같다. 전날 알림과의 차분 관리가 필요 없다 |
| 3 | 화면의 재고 조회(SCR-201) 「발주점 이하」 판정과 같은 조건식을 쓴다 | 화면과 알림의 결과가 어긋나는 것을 막는다. 조건식은 SQL 공통 부품(MyBatis `<sql>`)으로 한 곳에 정의 |

## 3. BAT-02 월별 재고 집계(monthlyStockSummaryJob)

| 항목 | 내용 |
|---|---|
| 기동 | 매월 1일 0:30(cron: `0 30 0 1 * *`) |
| 파라미터 | `targetMonth`(YYYYMM. 생략 시 실행일의 지난달), `launchedAt` |
| 구성 | 1스텝(태스크릿). `StockMonthlyService.summarize(targetMonth)` 호출 |
| 트랜잭션 | 전체가 한 트랜잭션 |

처리: ① 대상 연월의 월별 재고 삭제 ② `t_stock` 전 행을 대상 연월로 INSERT … SELECT ③ 등록 건수 반환

## 4. BAT-03 청구 마감(invoiceClosingJob)

| 항목 | 내용 |
|---|---|
| 기동 | 화면(SCR-501)의 「청구 마감 실행」에서 비동기로 기동 |
| 파라미터 | `closingDate`(마감일), `closingDay`(마감일 구분), `customerId`(선택), `executedBy`(실행자 사용자 ID), `launchedAt` |
| 구성 | 1스텝(청크 처리, 청크 크기 1) |
| 트랜잭션 | 매출처 1곳마다 커밋 |

| 역할 | 처리 |
|---|---|
| 읽기(Reader) | 스텝 시작 때 `InvoiceClosingService.findTargetCustomerIds`로 대상 매출처 ID 목록을 가져와 1건씩 돌려준다. Reader 빈은 `@StepScope`로 해서 실행마다 새로 만든다(싱글톤이면 두 번째 실행부터 이전 읽기 상태가 남아 0건으로 완료됨. 기술 검증 결과 보고서 6장 No.4) |
| 쓰기(Writer) | `InvoiceClosingService.closeCustomer(매출처 ID, 마감일, 실행자)` 호출. 청구가 만들어지면 생성 건수에 더한다 |

화면 쪽 흐름: 실행 중인 잡 확인(있으면 E-052) → 비동기 기동해 실행 ID를 받음 → 5초마다 status 조회해 실행 상황 표시

### 실행 상황 조회(GET /billing/closings/{실행 ID}/status)

| 항목 | 내용 |
|---|---|
| 돌려주는 내용 | 상태(실행 중/완료/이상 종료), 대상 매출처 수, 처리된 매출처 수, 생성 건수 |
| 취득처 | Spring Batch 실행 관리 정보(스텝의 읽기 건수·쓰기 건수) |
| 권한 | ACCOUNTING. 다른 잡(BAT-01, 02)의 실행 ID를 지정하면 404 |

### 설계상의 판단

| No | 판단 | 이유 |
|---|---|---|
| 1 | 청크 크기를 1(매출처 1곳마다 커밋)로 | 한 곳에서 에러가 나도 다른 매출처의 청구를 확정하기 위해. 또 출하 행 잠금을 오래 쥐지 않기 위해(마감 처리 중에도 출하 등록 가능) |
| 2 | 에러가 나면 그 매출처를 건너뛰지 않고 잡을 이상 종료로 | 일부 매출처만 청구가 안 만들어진 상태를 경리 담당이 모르고 지나가는 것을 막는다. 원인을 해소한 뒤 다시 실행 |
| 3 | Spring Batch의 재개 기능(리스타트)은 쓰지 않고 매번 새 실행으로 기동 | `closeCustomer`가 「미청구 출하만 대상」이라 다시 실행하면 처리되지 않은 분만 처리된다. 재개 위치 관리가 필요 없다 |
| 4 | 이중 기동은 실행 중인 잡 실행의 유무로 판정 | 동시에 실행돼도 데이터 정합성은 유지되지만(처리 상세 04의 7장) 사용자 혼란을 막기 위해 |
| 5 | 비동기 기동 | 5년 후 건수(260곳)에서 처리 시간이 수십 초~수 분이 될 수 있어 화면 응답을 기다리게 하지 않기 위해(NF-09) |

## 5. 이상 시 대응

| 사상 | 감지 | 대응 |
|---|---|---|
| BAT-01·02 이상 종료 | ERROR 로그를 모니터링이 감지해 개발 담당에게 통지 | 원인을 조사해 수동으로 다시 실행(운영 절차서에 절차를 정함). 재실행은 관리자용 명령 또는 관리용 엔드포인트로 |
| BAT-01·02가 정해진 시각까지 끝나지 않음 | 종료 로그가 나오지 않는 것을 모니터링이 감지 | 위와 같음 |
| BAT-03 이상 종료 | 화면에 E-090과 접수 번호 표시. ERROR 로그 | 경리 담당이 개발 담당에게 연락. 원인 해소 후 경리 담당이 화면에서 다시 실행 |
| 배치 실행 중에 애플리케이션이 멈춤 | 실행 관리 테이블에 「실행 중」으로 남음 | 기동 때 「실행 중」으로 남아 있는 잡 실행을 「이상 종료」로 갱신하는 처리를 한다(이중 기동 체크 때문에 기동 못 하게 되는 것을 막음). `StaleJobExecutionRecoverer`가 수행하고 WARN 로그 출력 |

## 6. 단위 테스트·통합 테스트 방침

| 대상 | 방법 |
|---|---|
| Service(rebuild, summarize, closeCustomer) | Testcontainers의 PostgreSQL을 써서 데이터를 넣고 결과를 검증(SQL의 정확성이 처리의 중심이라 Mapper를 목으로 만들지 않는다) |
| 잡 | Spring Batch 테스트 지원 기능으로 잡을 기동해 종료 상태와 건수 검증 |
| 재실행 | 같은 파라미터로 두 번 실행해 결과가 바뀌지 않는지(BAT-01, 02), 두 번째 생성 건수가 0인지(BAT-03) 확인 |
| 이상계 | `closeCustomer`가 두 번째 매출처에서 예외를 던졌을 때 첫 번째 매출처의 청구가 확정되고 잡이 이상 종료가 되는지 확인 |
